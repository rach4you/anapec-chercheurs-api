# WS_INSCRIPTION — Full Researcher Registration

## Purpose

Register a researcher completely in SIGEC inside a single DB transaction:
the `CHERCHEURS` master row plus all related rows (mobilites, diplomes,
experiences, bureautiques, permis, langues, emplois metiers). If any insert
fails, the entire operation is rolled back — no partial data ever survives.

## Endpoint

```
POST /api/v1/services/inscription
Authorization: Bearer {sanctum-token}
Content-Type: application/json
```

## Authentication & Authorization

- Requires Sanctum authentication
- User must be **active**
- User must have **WS_INSCRIPTION** permission enabled
- WS_INSCRIPTION must be **globally active**
- Rate limited: 60 requests/minute

## Required Fields

`chercheur.nationalite`, `chercheur.cin`, `chercheur.password`,
`chercheur.nom_candidat`, `chercheur.prenom`, `chercheur.sexe`,
`chercheur.situation_familiale`, `chercheur.date_naissance` (dd-mm-yyyy),
`chercheur.adresse`, `chercheur.ville_id`, `chercheur.commune_id`,
`chercheur.e_mail`, `chercheur.n_gsm`, `chercheur.situation_p_r_emploi`.

`chercheur.password` must be at least 6 characters, at most 30.
`chercheur.cin` must be between 2 and 15 characters.

All date fields (`date_naissance`, `date_debut`, `date_fin`,
`date_inscription`, `date_derniere_actualisation`) must use the format
`dd-mm-yyyy`.

## Server-side Behavior

- **CIN normalization**: the CIN is trimmed and uppercased before any
  duplicate check or insert.
- **Email duplicate check** is case-insensitive (`LOWER(e_mail) = LOWER(?)`).
- **`chercheur_id` is generated by the server** via the SIGEC sequence
  `chercheurs_seq` (populated by the `TRIG_CHERCEUR` BEFORE INSERT trigger).
  Any client-supplied `chercheur_id` or `id` field is silently dropped by
  validation (not listed in the rules).
- **`date_inscription` and `date_derniere_actualisation`** are always
  overwritten with the current date. Client-supplied values are ignored.
- **Duplicate languages**: within a single request, if two `langues` entries
  share the same `competence_linguistique_id`, only the first is inserted.

## Transaction Semantics

Every insert (CHERCHEURS + all 7 relation tables) runs inside a single
`DB::transaction()`. Any exception at any point — including a duplicate CIN
check failure, a relation insert failure, or an unexpected error — triggers
a full rollback. It is never possible to end up with a CHERCHEURS row but no
relations, or partially inserted relations.

## Responses

### 201 — Success

```json
{
  "success": true,
  "message": "Chercheur enregistré avec succès.",
  "data": {
    "chercheur_id": 9651573,
    "cin": "BJ5556",
    "email": "rachidlahmami@gmail.com"
  }
}
```

### 409 — Duplicate CIN

```json
{
  "success": false,
  "message": "Un chercheur existe déjà avec ce CIN.",
  "code": "CIN_ALREADY_EXISTS"
}
```

### 409 — Duplicate Email

```json
{
  "success": false,
  "message": "Un chercheur existe déjà avec cet email.",
  "code": "EMAIL_ALREADY_EXISTS"
}
```

### 422 — Validation Error

```json
{
  "success": false,
  "message": "Le champ cin est obligatoire.",
  "errors": {
    "chercheur.cin": ["Le champ cin est obligatoire."]
  }
}
```

### 401 / 403 — Auth Errors

See `WS_CHECK_CIN.md` — identical middleware behavior.

### 500 — Unexpected Error

If raised inside the transaction, the entire operation is rolled back. No
partial rows survive in SIGEC.

## Tables Written

| Table | Key columns |
|-------|-------------|
| `CHERCHEURS` | `CIN`, `PASSWORD`, `NOM_CANDIDAT`, `PRENOM`, `SEXE`, `SITUATION_FAMILIALE`, `DATE_NAISSANCE`, `ADRESSE`, `VILLE_ID`, `COMMUNE_ID`, `E_MAIL`, `N_GSM`, `SITUATION_P_R_EMPLOI`, `NATIONALITE`, `DATE_INSCRIPTION`, `DATE_DERNIERE_ACTUALISATION`, plus optional fields |
| `chercheurs_mobilites` | `mobilite_id`, `chercheur_id` |
| `bureautiques_chercheurs` | `chercheur_id`, `bureautique_id` |
| `avoir_permis` | `chercheur_id`, `permi_conduire_id`, `CIN` |
| `avoir_diplomes` | `chercheur_id`, `CIN`, `diplome_id`, `specialite_id`, `option_diplome_id`, `groupe_etablissement_id`, `etablissement_id`, `date_optention`, `commentaire` |
| `experience_proffes` | `chercheur_id`, `CIN`, `date_debut`, `date_fin`, `ce_jour`, `employeur`, `intitule_poste`, `commentaire`, `duree_experience_id` |
| `langues_parlees` | `chercheur_id`, `CIN`, `competence_linguistique_id`, `niveau` |
| `chercher_emplois` | `chercheur_id`, `CIN`, `emploi_metier_id` |

All relation rows carry the `chercheur_id` returned in the response.

## Security

- Parameterized queries only (no SQL concatenation)
- No Oracle error details exposed to the client
- Password stored in SIGEC as-is (VARCHAR2(30), legacy plain-text column)
- No tokens or secrets in the response
